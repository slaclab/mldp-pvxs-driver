Directory Service

Summary

The directory service ("DS") is a EPICS V4 data service that provides the names of PVs, devices, model elements, and other associated information about the components of the accelerator, to users and applications software. This information is obtained from multiple places.
  1. The list of of PV's is obtained from ${IOC_DATA}/**/iocInfo/IOC.pvlist
  2. The list of devices, model elements etc is obtained from the MAD export files located in /afs/slac/www/grp/ad/model/output/lcls/latest/opt. Please see the requirements doc for more details.
  3. User defined tags are obtained by parsing files in ${IOC_DATA}/../ds_tags ending with the extension .tag. The inital part of the file name is the name of the tag; the file contains a list of PV names. PV names can be regexes. The # character can be used to add comments to tag files; these lines are ignored. For example, this tag file defines the names for the tag MikeZ 
    
cat ${IOC_DATA}/../ds_tags/MikeZ.tag
#Sample list of tags for Mike Z
#One can use a pattern like so
SIOC:SYS0:ML01:AO%9
#Or an absolute list of PV's like so - this was generated using eget -t -s ds -a tag=LI22 -a name=KLYS:%:STATSUMY
KLYS:LI22:11:FOCUS:STATSUMY
KLYS:LI22:11:STATSUMY
KLYS:LI22:21:FOCUS:STATSUMY
KLYS:LI22:21:STATSUMY
...
Information from all of these sources is combined and indexed in the memory of the directory service and served thru a V4 API. For example, eget -s ds -a tag=QM15 gets all the PV's in the element QM15. eget -s ds -a elementname=QM15 -a name=%:STATSUMY gets all the PV's in the element QM15 matching the name %:STATSUMY. 

$ eget -s ds -a tag=QM15
                      name
   QUAD:LI21:335:STATMSGDP
   QUAD:LI21:335:STATMSGFP
   QUAD:LI21:335:STATMSGSV
    QUAD:LI21:335:STATSUMY
  QUAD:LI21:335:STATSUMYFP
      QUAD:LI21:335:TEMPDP
      QUAD:LI21:335:TEMPFP
      QUAD:LI21:335:TEMPSV

$ eget -s ds -a elementname=QM15 -a name=%:STATSUMY
                    name
  QUAD:LI21:335:STATSUMY
The directory service monitors these sources of information for any changes; detecting changes using the last modification timestamp.

Major components

The DS is a self-contained Java V4 application; it lives within a standard V4 container. The source repository (GIT) is located here - /afs/slac/g/cd/swe/git/repos/high_level_apps/directory_service.git
  1. DSMain is the main launcher and instantiates the V4 framework, a DSContainer object and the service implementation.
  2. DSContainer maintains all the information used by the directory service. All the others populate and use the information in the DSContainer. It is possible to switch the entire DSContainer object in a thread-safe fashion; there is an out-of-band command that does this today (this may be removed in the future).
  3. DSServiceImpl implements the V4 service API using the specified DSContainer.
  4. The DSContainer has an instance each of
    1. GatherIOCPVListFiles - This periodically walks ${IOC_DATA} and maintains a list of **/iocInfo/IOC.pvlist files.
    2. IOCPVListWatcher - This periodically checks the last modified times of the files identified by GatherIOCPVListFiles and kicks of changes to the list of PV names.
    3. IOC2PVNames - This manages the mapping between the specific IOC.pvlist and the PVNames that this contains.
    4. PVNames - This indexes and manages the global list of PV names. All name queries are executed against the information here using the findMatchingPVNames method.
    5. TagsFromDeck - This loads tag information from the MAD deck export and user defined tags and manages the mapping between tags/element names/device names etc and PV names.
The directory service API is complex and allows the user to match between a wide variety of name types(DSNameType). For example, we support the ability to get PV names given any combination of the element name/device name/line name/tag and so on. Navigation from each name type to another name type is implemented as an ExecutionPlan. The set of ExecutionPlan's in the system is registered in the ExecutionPlans. When we get a query for names, we
  1. Determine the destination name type
  2. Gather a list of source name types and arguments
  3. For each source name type, we determine the ExecutionPlan that can determine matching names from that source name type to the destination name type.
  4. The final result is the set intersection of all the matching names determined in the previous step.

Deployment

The DS is a crammable high-level app and thus lives in ${PHYSICS_TOP}. Per cram standards, it is fully self contained. To build, please use ant. To run the unit tests, please use ant test. In LCLS production, it typically takes about 1-2 minutes to start up (as it loads up all the information on startup). Most name matching queries seem to finish within a few milliseconds. The locations of all the various sources of information and the polling periods are all configurable using environment variables.
