Requirements for the directory service

Greg White, Murali Shankar, SLAC, Version 1.0 22-Jan-2015.

Abstract

The "Directory Service" is a computer software data service that provides the names of Process Variables (PVs), devices, model elements, and other associated information about the components of the accelerator, to users and applications software.
Requirements for the directory service are given, motivated by usage examples. Requirements are indicated with a "*", like this line.
  1. It's assumed that the EPICS Channel Finder will be used "under the covers" for IOC CA PV names.
  2. However, the requirements are given both without reference to EPICS Channel Finder, and also where appropriate illustrated with how the requirement might be satisfied by an EPICS V4 service on top of Channel Finder.

Users

The Directory Service (DS) will be used by end-user physics applications software in the SLAC control system, such as Matlab GUIs, and by operators and physicists. For instance, for finding lists of names of PVs matching some criteria, like all the BPMs in the L2 linac.
Such lists are used to construct Z-plots and other beamline oriented functions.

So, what's the difference between this doc and what we've got in the prototype ds?
  1. Easy intuitive ability to output element names. From Murali's first examples (Nov 6 below), you can get the element name as part of getting the list of all tags, but we need a way for physicists and easy coding that makes it easy to just get the element name
  2. Easy intuitive ability to output device names (not PV names). From Murali's first examples (Nov 6 below), you can get device names (egs 1,2 & 3) but it's not clear to me what he did to get that! Maybe can fix this by just more examples using "show" arg.
  3. Input element type (needs support from MAD publishing system)
  4. Output Z and ordinal (needs support from MAD publishing system)

Questions

  1. Do we want SUML as well as Z?
  2. Do we want "S for display" as well as Z?
  3. Cells and girder information?
  4. Do we want to mark some PVs as the primary READBACK or the primary SETPOINT? eg QUAD:LI21:335:BACT, BPMS:IN20:425:X etc. This would support pvManager, CSS displays etc. See "Primary PV of device" below.
  5. Do we want line begin and ending Z to support nice displays?
  6. How shall we maintain completeness and validity of element names and device names? See "Validation" below
  7. Do we want DS to be able to tell us the IOC of a PV? cainfo would give that if the IOC were up, but if the IOC is down, you may want ds to help in diagnosis
  8. Do we want DS to know the fields of records?

    • eget -s ds -a elementname=QM15 -a show=channelname

  • * Abbreviations for property names elementname, devicename and channelname SHOULD be supported. Suggest those in summary table above. [Q: I believe presently "name" implies channel name and is the default. But is it possible to get the device name or element name instead of channel name?]

User defined lists

The DS should support the ability to easily create and maintain new named lists of devices. For example, a user may want to make a list called Mike's Devices which includes, for example, BPMS:UND1:1690:X, BPMS:IN20:631:Y and PATT:SYS1:1:NSEC. Then, the user should be able to get this list using the tag=Mike's Devices, like so 

$ eget -t -s ds -a tag="Mike's Devices"
BPMS:UND1:1690:X
BPMS:IN20:631:Y
PATT:SYS1:1:NSEC

Systematics

The following are to do with requirements of for how the system is implemented rather that what it does for a user. User requirements are described above.
  1. IOC engineer adds new IOC record for added device.
  2. IOC changes IOC record name for device moved in beamline, per naming convention.
  3. Physicist adds new device to model online model - causing new device in MACHINE_MODELS
  4. Physicist adds new device to model online model - causing new device in MACHINE_MODELS
  5. Physicist (eg MDW) adds new device to offline MAD deck, and Andrea uploads to Oracle - causing new element and device in LCLS_ELEMENTS
  6. Physicist wants simple way to talk to an element through its common PVs.
  7. End user PV aliasing. DS names db should be designed and maintained with a view that it may be used to source EPICS PV aliasing, possibly in the gateway. So a physicist wouldn't need to know the device name. Eg, In the future, using information in the DS, we should have a small suite of user level commands and API that are be able to understand request to get value of, say, QM15:BDES. Eg 
    
  $ eget QM15:BDES
  12.233133
Systematic requirements
  1. * Maintain a "current" list of names
    1. PV names from from EPICS IOC's. Per Ernest, we can make an assumption that ${IOC_DATA}/*/iocInfo/IOC.pvlist will give us a list of valid PV's. The DS MUST be able to learn the existence of a new CA PV immediately (seconds or a few minutes) after its introduction. [SUC1, SUC2]
    2. PV names from EPICS v4 servers and pvdatabases.
      1. So far, there are only 3 v4 server PV names (optics, rdb, testservice). However, in future these systems will be changed so the PV name is not the name of the service (like "optics") but the name of quantities they serve (like YCOR:LI22:703:TWISS). That means many more PVs, and that means we need some way to harvest those names into the DS.
      2. Let's leave that for phase 2 though. It may be that the names will also be harvested from a file, or it may be that the DS can use the EPICS V4 facility for finding all the PVs offered by an online EPICS server by asking the server directly.
  2. * Maintain a "current" list of lines, element names, types and Z, from the MAD deck. The device name, element name and line information, should be harvested periodically from the "latest" directory of MAD optics.
    1. Per Greg, these are exported into a folder, for example, /afs/slac/www/grp/ad/model/output/lcls/latest/opt into three files.
      1. GSPEC_lines.dat
      2. LCLS_lines.dat
      3. SPEC_lines.dat
    2. Every line in these these files contains a device name, an element name, a device type, a SUML, a Z and a list of line names. For example, 
      YCOR:DMP1:298 YCUE2 VKIC 1703.767399 3718.423772 LCLS BSYLTU UNDEXIT UNDCL GIRD33 QBLK33 CHICANE  LIN22
      translates to where
      1. YCOR:DMP1:298 is the device name.
      2. YCUE2 is the element name.
      3. VKIC is the device type.
      4. 1703.767399 is the SUML.
      5. 3718.423772 is the Z.
      6. and the rest LCLS BSYLTU UNDEXIT UNDCL GIRD33 QBLK33 CHICANE LIN22 are line names.
    3. We match PV's belonging to a device by using the device name as the prefix of the PV name. For example, all PV's that start with the string YCOR:DMP1:298 belong to the device YCOR:DMP1:298 and hence are associated with the element name YCUE2 and the line names UNDEXIT....
    4. The same device can drive more than one element. For example, 
      KLYS:LI21:61 K21_6B ... L2
KLYS:LI21:61 K21_6C ... L2
KLYS:LI21:61 K21_6D ... L2
      the device KLYS:LI21:61 drives the three elements K21_6B, K21_6C, K21_6D.
  3. *Validation and completeness In the past keeping the names system (AIDA aidalist), up to date with respect to Oracle LCLS_INFRASTRUCTURE, the model system, and MAD decks, has been very labor intensive.
    • How to fix that? First, bypass the requirement for veracity and up-to-dateness of Oracle LCLS_INFRASTRUCTURE with respect to device names. That would mean applications would work whether LCLS_INFRASTRUCTURE had been updated with device names or not. Instead, applications would use the directory service. It would source the association of device names to element names from elementdevices.dat [1].
    • To verify completeness, I can write a script that checks whether all elements of "control system type" have an assigned device name in elementdevices.dat. That check could be made in mad2dot.awk [2] at the block beginning "if ( name in elementdevNamem )".
    • It would be run by the MAD publication process. It would refuse to install files to /grp/ad/model/output/lcls/ unless the check passed.
    • In this way, the mad deck publishing process [3] can be used to ensure that whenever a new MAD deck is published for use, every element that should have an assigned device name has one.
  4. *Up-to-dateness - Data MUST be up-to-date with respect to the input sources above by at-most a "few minutes," say 5 minutes. Therefore, if an IOC gets rebooted, we pick up the changes within 5 minutes. The duration of the "few minutes" window should be configurable in some way.
  5. Data will be returned as an EPICS V4 NTTable. 
    $ eget -N -s mds -a tag=K23_7 -a name=%:STATSUMY
epics:nt/NTTable:1.0
string[] labels [name]
structure value
string[] name 
  [XCOR:LI23:702:STATSUMY,BPMS:LI23:801:STATSUMY,KLYS:LI23:71:STATSUMY,YCOR:LI23:703:STATSUMY
  6. Performance. Matching list SHOULD be returned in < ~0.5 s (mean first access time).

Future

Primary PV of device
An engineer who doesn't know the naming convention of PVs at SLAC wants to know the setpoint and readback values of a given quadrupole: They may want to use tags like "setpoint" and "readback" to determine which PVs are of interest.
For example, query the Directory Service to tell us the readback PV of QUAD:LI21:335:
eget -s ds -a devicename=QUAD:LI21:335 -a handle=readback
QUAD:LI21:335:BACT
Using the element to device name translation (above) and primary readback/ setpoint support, then the most elegant and simple end user interface is possible.
For examples: get the value of QM15:
eget qm15
34.34535
or to put to qm15: 

eput qm15 3.45

Other systems

To support these requirements, other systems must be modified:
  1. mad2awk.dat modified to check that all control system elements have an assigned device in elementdevices.dat [1]
  2. mad2awk.dat must be modified so that the lines files it emits (LCLS_lines.dat etc) include also MAD element type (MONI, QUAD, HKIC etc) and Z. Possibly also suml
  3. V4 EPICS servers (non-pvDatabase) will need to publish their PV lists somewhere so the DS can harvest them.
