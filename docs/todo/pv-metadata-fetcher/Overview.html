Directory Service Overview

Summary

The directory service ("DS") is a EPICS V4 data service that provides the names of PVs, devices, model elements, and other associated information about the components of the accelerator, to users and applications software. You use the DS just like you'd use any other V4 service. 

[softegr@lcls-builder mshankar]$ eget -s ds -a name=BPMS:LI21:%:X
             name
  BPMS:LI21:131:X
  BPMS:LI21:161:X
  BPMS:LI21:201:X
  BPMS:LI21:233:X
...

Data sources

The DS integrates information from multiple sources.
  • The list of of PV's is obtained from ${IOC_DATA}/iocName/iocInfo/IOC.pvlist.
    • IOC's using the standard startup commands typically use a command similar to iocshCmd("dbl '' RTYP > ${IOC_DATA}/${IOC}/iocInfo/IOC.pvlist") to dump a list of their PV's into a file called IOC.pvlist.
    • For example, the IOC sioc-bsy0-tm01 will dump its list of PVs into ${IOC_DATA}/sioc-bsy0-tm01/iocInfo/IOC.pvlist.
    • The DS monitors all files matching the path ${IOC_DATA}/**/iocInfo/IOC.pvlist and uses this to build a list of all PV's in the accelerator.
    • Many V4 services also export their accelerator specific PV's using a similar mechanism. For example, the optics service adds it's TWISS V4 PV's to the DS by dumping its PV list to ${IOC_DATA}/../ds_tags/otherNames/optics_channels.xdb.
  • Greg White's team exports the MAD deck periodically into files located in the folder /afs/slac/www/grp/ad/model/output/lcls/latest/opt
    • The files GSPEC_lines.dat, LCLS_lines.dat and SPEC_lines.dat contain information that map deviceName's to other information.
    • Every line in these these files contains a device name, an element name, a device type, a SUML, a Z and a list of line names. For example,
      YCOR:DMP1:298 YCUE2 VKIC 1703.767399 3718.423772 LCLS BSYLTU UNDEXIT UNDCL GIRD33 QBLK33
      translates to where
      1. YCOR:DMP1:298 is the device name.
      2. YCUE2 is the element name.
      3. VKIC is the device type.
      4. 1703.767399 is the SUML.
      5. 3718.423772 is the Z.
      6. and the rest LCLS BSYLTU UNDEXIT UNDCL GIRD33 QBLK33 are line names.
    • PV's "belong" to a device if the PV name starts with the device name.
      • For example, using the previous line, all PV's that start with the string YCOR:DMP1:298 belong to the device YCOR:DMP1:298 and hence are associated with the element name YCUE2 and the line names UNDEXIT....
    • The DS considers devices, elements and lines as "tags" and associates every PV with many tags. You can then search of PV's that are associated with a tag.
  • In addition to the tags from the MAD deck, you can define your own tags that map to channel names and devices. The DS looks for user defined tags in files with the .tag suffix in ${IOC_DATA}/../ds_tags. For example, here's a tag definition file for a tag called mMisc. 
    [mshankar@lcls-dev2 ~]$ cat ${IOC_DATA}/../ds_tags/mMisc.tag
# Match names using a pattern
BPMS:%:X
# Match names using absolute names
VPIO:UND1:1010:LEFF
# Specify using device names
devicename=QUAD:IN20:831
devicename=XCOR:IN20:491
    A tag file is a list of name patterns.
    • You can add comments by prefixing the line using a # character.
    • You can add all names that match a PV name pattern using a name pattern. For example, the pattern BPMS:%:X add's all BPM X's.
    • Absolute names without a pattern can be added as well.
    • You can add all PV names that "belong" to a device by using a devicename argument. For example, devicename=QUAD:IN20:831 adds all PV's "belong"ing to the device QUAD:IN20:831.

Examples

  • The most common usecase for the DS is to find names that match a pattern. Here's all the BDES's in the accelerator. 
    [softegr@lcls-builder mshankar]$ eget -t -s ds -a name=%:BDES
BEND:DMP1:400:BDES
BEND:DMP1:410:BDES
BEND:DMP1:420:BDES
...
  • The DS has special names for PV names and the tags that are imported from the MAD deck and elsewhere.
    AttributeDS Argument nameExample
    PVsname or channelnameQUAD:LI21:335:BDES
    Device Namedname or devicenameQUAD:LI21:335
    Element Nameename or elementnameQM15
    Linelname or linenameL2
    Element Typeetype or elementtypeQUAD, HKIC etc
    Zz34.34535
    IOCiocSIOC:NEH1:WA01
  • Thus, you can get the PV's that "belong" to a device 
    [softegr@lcls-builder mshankar]$ eget -t -s ds -a dname=BPMS:LI21:131
BPMS:LI21:131:ACCESS
BPMS:LI21:131:ACTL
BPMS:LI21:131:AODL
BPMS:LI21:131:ASIM
BPMS:LI21:131:ASUB_LKUOFFSET
...
  • You can also determine which elements are driven by a device by using the show argument. 
    [softegr@lcls-builder mshankar]$ eget -t -s ds -a dname=KLYS:LI21:61 -a show=ename
K21_6B
K21_6C
K21_6D
  • By default, if you don't specify the show argument, the DS show's PV names. That is, the default value for the show argument is name.
  • cainfo often does not tell you which IOC is hosting a PV. You can use the DS to quickly find this. 
    [softegr@lcls-builder mshankar]$ eget -t -s ds -a name=WATR:NEH1:950:RETURN_TEMP -a show=ioc
SIOC:NEH1:WA01
    You can do some shell script magic to find the IOC engineers for all TEMP's in the system. 
    [softegr@lcls-builder mshankar]$ eget -t -s ds -a name="%:TEMP" -a show=ioc \ 
| sed 's/.*/\0:CONTACT/' | grep -v -e '^:CONTACT' | xargs caget 
IOC:IN20:TM01:CONTACT          Sonya Hoobler (sonya)
IOC:LI20:CV01:CONTACT          Kristi Luchini (luchini)
IOC:LI21:CV01:CONTACT          Kristi Luchini (luchini)
...
  • You can search for names using your custom tag's. 
    eget -t -s ds -a tag=mMisc
BPMS:IN20:221:X
BPMS:IN20:235:X
...
QUAD:IN20:831:ACCESS
QUAD:IN20:831:BACT
...
QUAD:IN20:831:Z
VPIO:UND1:1010:LEFF
...
XCOR:IN20:491:ACCESS
XCOR:IN20:491:BACT
...
  • You can combine tags and names in various ways. For example, you can find all the devices in the line GUNBXG using 
    [softegr@lcls-builder mshankar]$ eget -t -s ds -a lname=GUNBXG -a show=dname
BPMS:IN20:221
CATH:IN20:111
FARC:IN20:212
MIRR:IN20:181
  • You can combine search terms; for example, you can find all QUAD BDES's in the line GUNBXG using 
    [softegr@lcls-builder mshankar]$ eget -t -s ds -a lname=GUNBXG -a name="QUAD:%:BDES"
QUAD:IN20:121:BDES
QUAD:IN20:122:BDES
    In this case, the query translates to lname=GUNBXG AND name="QUAD:%:BDES".
  • The DS has limited support for OR's. For example, 
    [softegr@lcls-builder mshankar]$ eget -t -s ds -a lname=GUNBXG,GSPEC -a name="QUAD:%:BDES"
QUAD:IN20:121:BDES
QUAD:IN20:122:BDES
QUAD:IN20:811:BDES
QUAD:IN20:831:BDES
    translates to (lname=GUNBXG OR lname=GSPEC) AND name="QUAD:%:BDES"
  • By default, the DS sorts the names alphabetically. However, you can sort by other parameters. For example, here's the BPM X's sorted by location in the accelerator (the Z index). 
    [softegr@lcls-builder mshankar]$ eget -t -s ds -a name=BPMS:%:X -a sort=z
BPMS:IN20:821:X
BPMS:IN20:221:X
...
BPMS:LI21:901:X
BPMS:LI22:201:X
BPMS:LI22:301:X
BPMS:LI22:401:X
...
  • There are many more ways you can use the DS. You can get online help using 
    eget -s ds -a help
    This also includes some sample Python code that can be used as a starting point for Python applications.

Latency

The DS does not immediately reflect the changes to IOC files, MAD exports, user tags and other sources of information. There is a time delay negotiated with the systems team to avoid stressing the file system. This can be changed if it proves to be too cumbersome.
  • Changes to existing IOC.pvlist files after IOC reboots should typically be reflected in the DS within 2-5 minutes.
  • Changes to user defined tags and MAD deck exports should typically be reflected in the DS within 5-10 minutes.
  • Brand new IOC.pvlist files should typically be reflected in the DS within 30-60 minutes.
Source of changeReflected in DS within
Existing IOC.pvlist2-5 minutes
Updated MAD deck export5-10 minutes
New or updated user defined tag5-10 minutes
New IOC.pvlist30-60 minutes

Optimizing DS queries

The accelerator facilities at SLAC use a well-defined naming scheme for EPICS PV's. This naming scheme has the following structure
DeviceType : Area : Position : Attribute
For example, the PV name QUAD:LI21:131:BDES can be broken into these components
QUAD : LI21 : 131 : BDES
Thus, the PV QUAD:LI21:131:BDES refers to a Quadrupole Magnet in the sector LI21 for the device in position 131 and specifies the desired B field for this quad.
The DS leverages this naming scheme to optimize name searches. For example, the search 
eget -t -s ds -a name=QUAD%BDES
is a search for all PV names that have the string QUAD as the prefix and the string BDES as the suffix. This search involves matching against a larger set of PV names and can take 100's of milliseconds. However, the similar search 
eget -t -s ds -a name=QUAD:%:BDES
is a search for all desired B field's in Quadrupole Magnet's. This search only involves matching against desired B field PV's in Quadrupole Magnet's. This is a much smaller set and therefore the search completes in less than a couple of milliseconds.
In general, to get the best results from the DS, try making your searches as specific as possible. Don't forget those colon's.
